## Phase 1 — libp2p request_response Behaviour

Add `request_response` to `ForetiasBehaviour` so the swarm can send/receive JSON-RPC over multiplexed streams.

### 1.1 ForetiasRpcProtocol

- [ ] Create `p2p/foretias-node/src/communerd/p2p/rpc_protocol.rs`
  - Implement `libp2p::request_response::Protocol` trait
  - Protocol name: `/foretias/{namespace}/rpc/1.0.0`
  - Inbound/outbound encoding: raw bytes (serde_json handles JSON)
  - Timeout: configurable (default 5s)
  - Accept all peers (no peer filtering at protocol level)

### 1.2 ForetiasBehaviour

- [ ] Add `request_response` field to `ForetiasBehaviour` in `p2p/behaviour.rs`
  - Use `request_response::Behaviour::new(ForetiasRpcProtocol::new(namespace), request_response::Config::default())`
  - Add `request_response` variant to `ForetiasBehaviourEvent` enum (auto-generated by derive macro)

### 1.3 ForetiasBehaviourEvent

- [ ] `#[derive(NetworkBehaviour)]` will auto-generate `ForetiasBehaviourEvent::RequestResponse(...)` — verify compilation

## Phase 2 — SwarmCommand Extension

Add RPC sending capability to the swarm loop.

### 2.1 SwarmCommand::RequestResponse

- [ ] Add variant to `SwarmCommand` in `p2p/swarm.rs`:
  ```rust
  RequestResponse {
      peer_id: PeerId,
      request: serde_json::Value,
      reply: tokio::sync::oneshot::Sender<Result<serde_json::Value, TransportError>>,
  }
  ```

### 2.2 SwarmCommand::DialPeer (if not already present)

- [ ] Verify `Dial { addr }` exists (it does). No change needed.

### 2.3 swarm_loop — Handle RequestResponse Command

- [ ] In `swarm_loop`, add handler for `SwarmCommand::RequestResponse`:
  - Serialize `request` to bytes via `serde_json::to_vec`
  - Call `swarm.behaviour_mut().request_response.send_request(&peer_id, bytes, protocol)`
  - Store `reply` sender in a `HashMap<RequestId, Sender>` for correlation

### 2.4 swarm_loop — Handle RequestResponse OutboundResponse Event

- [ ] In the `SwarmEvent::Behaviour(ForetiasBehaviourEvent::RequestResponse(...))` match arm:
  - On `OutboundRequestCompleted { request_id, response, .. }`: deserialize response, send via oneshot
  - On `OutboundRequestFailed { request_id, error, .. }`: send error via oneshot
  - On `InboundFailure { .. }`: log warning (no action needed — this is for the server side)

### 2.5 swarm_loop — Handle InboundRequest Event (Server Side)

- [ ] On `InboundRequest { peer, request, channel, .. }`:
  - Deserialize request as JSON-RPC 2.0
  - **Forward to the JSON-RPC handler** — this is the critical integration point
  - The server-side JSON-RPC handler already lives in `server/mod.rs`
  - Route: receive request → dispatch to appropriate handler (stamp, verify, get_calendar_slice, ping) → send response back via `channel`
  - This replaces (or sits alongside) the existing HTTP/JSON-RPC handler for libp2p-originated requests

## Phase 3 — Libp2pTransport

New transport implementation.

### 3.1 Create `libp2p_transport.rs`

- [ ] Create `p2p/foretias-node/src/communerd/libp2p_transport.rs`
  - Struct: `Libp2pTransport { cmd_tx, local_peer_id, timeout_secs, namespace }`
  - Implements `PeerTransport` trait
  - Each method constructs a JSON-RPC request, sends via `SwarmCommand::RequestResponse`, awaits oneshot reply
  - On timeout or oneshot error → fall back is handled at Communerd level (not here)

### 3.2 Method Implementations

- [ ] `stamp()` — build `{"jsonrpc":"2.0","method":"stamp","params":{...},"id":1}`, send, receive
- [ ] `route_stamp()` — same pattern with `route_stamp` method
- [ ] `get_calendar_slice()` — same pattern, deserialize result as `Vec<TickRecord>`
- [ ] `ping()` — same pattern, ignore result

### 3.3 Peer Resolution

- [ ] `Libp2pTransport::stamp()` requires `peer.peer_id` to be `Some`. If `None`, return `TransportError::Unsupported("peer has no libp2p PeerId")`

### 3.4 Startup Warning

## Phase 5 — Server-Side Handling of Inbound libp2p RPC

When peer A sends a JSON-RPC request over libp2p to peer B, B's server must handle it.

### 5.1 Route inbound requests to existing handlers

- [ ] In `swarm_loop`, when `InboundRequest` arrives:
  - Deserialize as `serde_json::Value`
  - Extract `method` and `params`
  - Dispatch to the appropriate handler in `server/mod.rs`
  - This requires the swarm loop to hold a reference to the server (or the handler functions)
  - **Approach:** Pass an `Arc<dyn CommunerdRpcHandler>` trait into `build_and_spawn_swarm`

### 5.2 CommunerdRpcHandler trait

- [ ] Define trait:
  ```rust
  #[async_trait]
  pub trait CommunerdRpcHandler: Send + Sync {
      async fn handle(&self, method: &str, params: serde_json::Value) -> Result<serde_json::Value, TransportError>;
  }
  ```

### 5.3 Implement CommunerdRpcHandler for TimeFamilyServer

- [ ] `TimeFamilyServer` already has stamp, verify, get_calendar_slice methods
- [ ] Implement `CommunerdRpcHandler` that maps JSON-RPC method names to these methods

### 5.4 Wire handler into swarm construction

- [ ] `build_and_spawn_swarm` takes an optional `Arc<dyn CommunerdRpcHandler>` parameter
- [ ] On `InboundRequest`, call handler, send response back via `channel.send_response()`
